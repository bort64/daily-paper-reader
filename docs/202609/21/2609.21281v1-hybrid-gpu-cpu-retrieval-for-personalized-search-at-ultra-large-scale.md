## 摘要
在万亿文档规模下，基于嵌入的用户生成内容检索暴露出两项生产需求之间的尖锐冲突：针对具有丰富用户意图的查询实现深度、富有表现力的个性化，以及在固定时延和资源预算下广泛覆盖海量物品库。我们将此称为个性化-规模悖论：将完整服务物品库托管在 GPU 内存中资源消耗过高，而 CPU 计算无法在时延关键路径上执行同样的交互密集型模型。我们提出一种 GPU-CPU 混合协同服务系统，通过编排而非新的模型类别来解决该悖论。一条高深度 GPU 路径在约十亿文档量级的精选在线池上融合检索与交互预排序，而一条高广度 CPU 路径则以轻量级个性化打分搜索独立选择的、规模约大二十倍的在线物品库。每个请求可运行其中一条或两条路径；候选在共享的下游排序之前进行去重。该系统已部署于生产环境。与原有仅 CPU 配置进行的全系统 A/B 测试提升了模型评分相关性和实质性参与度，而单独的路径实验也在各自部署范围内显示出正向价值。检索日志显示这些路径贡献了结构上不同的候选，生产服务测量刻画了它们的时延，匹配的容量规划量化了将建模深度分配给 GPU、将物品库广度分配给 CPU 的经济依据。总之，这些结果验证了一种实用、可独立演进的深度-广度架构，适用于超大规模个性化搜索。

## Abstract
Embedding-based retrieval on user-generated content at the trillion-document scale exposes a sharp conflict between two production demands: deep, expressive personalization for queries with rich user intent, and broad coverage of a massive inventory under fixed latency and resource budgets. We characterize this as the personalization-scale paradox: hosting the full serving inventory in GPU memory is too resource intensive, while CPU compute cannot execute the same interaction-heavy model on the latency-critical path.   We present a hybrid GPU-CPU co-serving system that resolves the paradox through orchestration rather than a new model class. A high-depth GPU pathway fuses retrieval and interaction pre-ranking over a curated online pool on the order of a billion documents, while a high-breadth CPU pathway searches an independently selected online inventory roughly twenty times larger with lightweight personalized scoring. Either or both pathways can run per request; candidates are deduplicated before shared downstream ranking.   The system is deployed in production. A full-system A/B test against the legacy CPU-only configuration improves model-scored relevance and substantive engagement, while separate pathway experiments show positive value at their own deployment scopes. Retrieval logs show that the pathways contribute structurally distinct candidates, production serving measurements characterize their latency, and a matched capacity plan quantifies the economic rationale for assigning modeling depth to GPUs and inventory breadth to CPUs. Together, these results validate a practical, independently evolvable depth-breadth architecture for ultra-large-scale personalized search.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：在万亿文档规模的用户生成内容（UGC）上进行基于嵌入的检索，同时面临两项生产级需求：
  - **深度个性化**：对具有丰富用户意图的查询（如发现类查询），需要非线性交互与行为历史建模；
  - **广覆盖库存**：对导航类、长尾特定查询，需要从海量物品库中召回稀疏文档。
- **核心矛盾——"个性化-规模悖论"（personalization–scale paradox）**：
  - GPU 具备深度交互建模能力，但其高带宽显存（HBM）无法经济地容纳完整在线库存；
  - CPU 具备廉价的大容量，但无法在延迟关键路径上运行同等交互密集的模型。
- **UGC 加剧矛盾**：兴趣随时间演化、新内容不断产生、过期/删除/违规内容不断消失，服务端必须支持随用户条件变化的分数与频繁刷新的广覆盖。
- **现有评测盲区**：仅衡量全精度模型质量或 ANN 召回率，都会遗漏目标的一端。
- **论文定位**：不去发明新的模型类别，而是通过**编排（orchestration）**——异构 GPU/CPU 协同服务——来解决该悖论。

## 2. 方法论：核心思想与关键技术细节

### 2.1 总体架构：深度-广度双路径共服务

- **GPU 高深度路径**：在约**十亿文档**量级的精选在线池上，融合 ANN 检索与交互预排序（fused pre-ranking）。
- **CPU 高广度路径**：在独立选择的、约**二十倍大**（数十亿量级）的在线库存上，以轻量级个性化打分做语义检索。
- **请求级编排**：两条路径可单独或同时运行；各自拥有独立 deadline、独立版本化发布、独立回滚能力；在**候选聚合器**处按文档 ID 去重并保留来源归属，再送入共享下游排序器。
- **失败隔离**：fork–join 边界使单条慢路径不会丢弃另一条路径已按时返回的结果。
- **库存选择**：多万亿源语料经策略、质量、语言、时效、去重检查后，由硬件特定选择器分别产出 GPU 快照与 CPU 索引；CPU 索引并非"低热度内容集合"，也包含可进入 GPU 池的热门文档，二者包含关系随版本变化。

### 2.2 GPU 路径关键技术

- **精选池构建**：以"搜索价值（search value）"而非原始热度为目标；三阶段生命周期过滤（摄入期硬元数据门控 → 首周早期互动过滤 → 第 7 天起分类/搜索有用性/本地信息/时间衰减模型）；类别自适应衰减（小众教程、本地指南绕过互动剪枝，新闻趋势快速衰减）；高度选择性的常青池对一年以上内容保留率低于 0.1%。
- **模型架构**：两塔检索器 + 基于 DeepFM 的交互预排序器联合训练。查询塔将 384 维语义嵌入与 128 维用户画像嵌入拼成 512 维稠密输入，经残差 MLP 与稀疏类别上下文处理；文档塔输出 128 维向量用于近邻检索。
- **联合训练损失**（式 1）：
  - **LTotal = w₁·LInfoNCE + w₂·L_SmoothL1 + w₃·L_BCE**
  - 跨会话 InfoNCE：批内以其他会话文档为负样本，学习 ANN 空间；
  - 会话内 InfoNCE：将已互动候选作为正样本、相关但未互动候选作为更难负样本；
  - Smooth L1 建模相关性，BCE 建模互动；加权价值模型 S_final = Σ_t λ_t·p̂_t，按流量分群调整权重，同一模型可服务异构流量而无需重训。
- **训练生命周期**：预排序器基于每日刷新的搜索日志持续训练；模型权重与候选索引**同步发布**，保证语料视图一致；每日索引刷新节奏由应用时效需求而非硬件限制决定。
- **加速器常驻服务**（沿用 SilverTorch 思路）：ANN 搜索、推理、预排序全程驻留加速器，避免 CPU–GPU 传输割裂检索与打分；稠密计算骨干驻 HBM，稀疏嵌入表按需经 **PCIe Gen5** 从主机内存拉取；**融合 8-bit 整数核**将量化与距离计算合并为一个算子；部署硬件为 **AMD MI300X**。

### 2.3 CPU 路径关键技术

- **架构**：预训练质心驱动倒排嵌入列表；查询先选邻近质心做粗剪枝，再扫描选中列表并结合余弦相似度与轻量词法信号；独立的文档理解服务消费实时创建/更新流与静态池，解耦嵌入生成与检索服务。
- **专用嵌入索引**：此前嵌入检索依附于词法索引子集，受词项抽象与延迟敏感负载争抢；独立索引使池扩大一个数量级以上，覆盖数十亿公开文档，按语言、时效、最低质量筛选，文档/嵌入/最小词法信号在 x86 DRAM 中分区复制；批构建基础索引 + 在线服务更新。
- **分布式质心训练**：池扩大 10 倍需按比例增加质心；原方案每分片独立训练 64k 质心，扩展到 512k 会阻塞部署。改为**训练与索引解耦**：独立分布式训练器每日跨多机运行，物化版本化质心索引后供各服务分片摄入，索引服务器不再重复聚类。
- **高效服务两优化**：
  - **Eager evaluation**：反转查询计划，先以 term-at-a-time（TAAT）连续读扫描近邻簇计算全局 Top-K，再以该候选列表作为剩余 DAAT 约束的动态跳表；把散乱随机读转为顺序扫描，避免对不可能入选文档做昂贵距离计算。
  - **Hit scanning**：绕过逐命中文档的迭代器虚函数调用，将原始向量批量传给 **AVX-512** 列表扫描核，把周期从分发/指针追逐转移到有效距离计算。
- **轻量个性化建模**：用户-查询塔与文档塔共享微调 **XLM-V** 骨干，以**双向 InfoNCE** 训练产出 384 维多语言紧凑向量；注意力模块通过池化嵌入查找融合稠密查询表示与稀疏上下文特征。用户与文档向量仅做点积交互，排除交叉特征交互，特征限于轻量画像、粗粒度上下文与历史信号，使文档向量可预计算、扫描适配 SIMD 执行——以表达力换取库存广度。

## 6. 主要结论与发现

- **全系统价值**：九日内，混合系统相对 legacy 全 CPU 配置，等日平均 **DCG@20 提升 4.51%**（保守 95% CI [+3.99%, +5.04%]），**GSRR 提升 2.01%**（[+1.71%, +2.32%]）；两项指标每日区间均为正。
- **路径级价值**：
  - GPU 高深度路径（七日）：**GSRR +1.04% ± 0.13%**，**DCG@20 +0.73% ± 0.15%**；
  - CPU 广库存路径（九日，GPU 关闭）：**GSRR +1.20% ± 0.11%**，**DCG@20 +3.16% ± 0.15%**。
- **候选结构互补**：三日约 11.4 万请求中，GPU 与 CPU 稠密检索集合重叠极低（head GPU-side 2.41%、CPU-side 1.15%、Jaccard 0.75%；torso/tail 更低），说明两路径贡献结构上不同的候选。
- **共享排序器输入组成**：每请求平均约 781 个去重候选，其中 GPU-only 209（27%）、dense CPU-only 47（6%）、lexical CPU-only 500（64%）、跨组重叠 26（3%）。
- **候选流转**：GPU 路径检索 594、送入排序器 224（reach 37.6%）；稠密 CPU 并集检索 1,352、送入 59（reach 4.4%）——两条流水线候选预算与过滤阶段不同。
- **时延**：CPU 路径在 P50/P95/P99 均快于词法检索；GPU 路径 P50/P95 更快，P99 高约 16%，但并非同口径核比较（GPU 做了交互预排序且送 224 候选，CPU 送 59）。
- **效率收益**：专用索引与 eager 执行使检索阶段计算降低 **89.45%（9.48×）**；15 天实验显示 512k 质心 + n_probe=256 配置**降低 CPU 使用 63.5%** 且未检测到 GSRR 回退（两项降幅基线不同，分别报告）。
- **经济性**：匹配容量规划中，加速器单位容量成本约为 CPU 的 **12×**，但单位向量容量高 2–3 倍、单位吞吐高 3–4 倍，单区域用约 1/3 单元数，三区域总容量成本比约 **4×**。
- **架构启示**：超大规模个性化检索无需强迫单一硬件层优化互相冲突的目标；异构路径可各自专业化、独立演进，并以"生产捆绑包"形式评估。

## 7. 优点

- **问题刻画清晰**：将工程矛盾抽象为"个性化-规模悖论"，并明确深度与广度消耗不同资源（交互→单候选计算，长尾→内存与扫描成本）。
- **编排优先的设计哲学**：不造新模型，而是用稳定"候选契约"（各路径自治库存、模型、资格、发布节奏、deadline、回滚；聚合器管去重与来源归属）实现两条路径独立演进与独立回滚。
- **深度与广度各有针对性优化**：GPU 侧融合检索与交互预排序、稀疏表走 PCIe、8-bit 融合核；CPU 侧专用索引、分布式质心训练解耦、TAAT eager evaluation、AVX-512 hit scanning，均紧扣各自瓶颈。
- **生产级验证与诚实披露**：全部结论来自线上 A/B 与真实日志，而非离线指标；明确区分系统级证据、路径级证据与结构冗余证据的适用范围。
- **统计方法稳健**：针对账号跨日复用，不简单除以 √9，而用 Cauchy–Schwarz 界给出对任意跨日依赖保守的置信区间，并报告每日区间均显著为正。
- **前瞻性洞察**

- **前瞻性洞察**：论文并不把 GPU/CPU 混合视为一次性工程技巧，而是提出"硬件层专业化 + 契约式编排"可能成为超大规模检索的长期范式——随着加速器算力与内存继续演进，哪些路径该放在哪类硬件上会持续重新平衡，而候选契约、来源归属、独立发布与回滚这些编排机制则是可复用的稳定抽象。

## 8. 局限与不足（论文自身披露 + 读者视角）

- **组件归因缺失（最核心的局限）**：
  - 每条路径的实验都同时改变了硬件、模型、库存池、ANN 精度与过滤器等多个变量，因此报告的增益是"完整路径的净效果"，无法拆解为单个因素的贡献；
  - 论文明确承认只做"full-path estimation"而非组件级归因，读者无法知道若只换模型或只扩库存能带来多少收益。
- **可比性受限**：
  - 表 2 各行来自不同实验窗口、不同对照组，行间数值不可直接相加或比较；
  - 时延对比并非同口径（GPU 路径做了交互预排序且送入 224 个候选，CPU 路径仅送 59 个），因此"GPU P99 高约 16%"不能简单解读为 GPU 更慢。
- **可复现性受限**：
  - 生产配置、隐私敏感日志、训练硬件与集群规模均未披露；
  - 论文自陈外部研究者难以复现，方法更多是"设计原则"而非可照搬的配方。
- **未覆盖的评估维度**：
  - 未做学习式请求路由（learned routing）的随机化评估，请求级编排策略的效果未量化；
  - 未验证子群体公平性、创作者曝光分布、生态健康度等长期指标；
  - DCG@20 非人工标注，其解读依赖行为信号，存在与真实相关性偏离的风险。
- **指标单点性**：
  - 主要结论建立在 DCG@20 与 GSRR 两个指标上，缺乏多样性、新鲜度、作者覆盖等辅助业务指标的交叉印证。

## 9. 潜在改进方向与启示

- **补做隔离式消融**：在受控流量桶中分别只切换模型、只扩库存、只调 ANN 精度，量化各因素边际贡献，补齐归因短板。
- **学习式请求路由**：当前两条路径"可单独或同时运行"，但如何决定何时启用哪条路径未展开；引入可随机化评估的路由策略，有望在延迟预算内进一步优化深度-广度权衡。
- **路径级预算自适应**：既然候选预算与过滤阶段不同（GPU reach 37.6% vs 稠密 CPU 4.4%），可按查询类型动态调整各路径的候选配额与 deadline。
- **质心规模与成本的连续调优**：512k 质心 + n_probe=256 已显示降本 63.5% 且无回退，说明召回-成本前沿仍有继续搜索的空间。
- **向其他模态/任务迁移**：候选契约、来源归属、独立回滚等编排抽象可推广到多模态检索、推荐与广告等同样面临"个性化-规模悖论"的场景。

## 10. 总体评价

- **学术贡献定位**：本文的价值不在提出新模型，而在于**系统级的问题重述与工程范式的提炼**——把"深度 vs 广度"的冲突显式化为可编排、可独立演进的异构路径，并用生产 A/B 数据证明其净收益。
- **证据强度**：系统级证据（DCG@20 +4.51%、GSRR +2.01%，九日保守区间均为正）与结构互补证据（两路径候选重叠极低）相互支撑，结论可信度高；但机制归因证据薄弱，作者对此披露诚实。
- **实践意义**：对同样面对海量 UGC、需要兼顾发现类与导航类查询的工业检索系统，本文提供的"GPU 高深度 + CPU 高广度 + 契约式编排 + 独立发布回滚"架构具有直接参考价值；经济性分析（三区域总容量成本约 4×）也为硬件投资决策提供了量化依据。
- **一句话总结**：这是一篇以生产验证为核心的**系统工程论文**，其最大启示是——当两个目标消耗不同资源时，与其强迫单一硬件层做折中，不如让异构路径各自专业化，再用稳定契约把它们编排起来。
