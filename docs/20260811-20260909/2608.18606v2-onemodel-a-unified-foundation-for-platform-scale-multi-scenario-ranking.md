## 摘要
平台级推荐系统通常跨越多个业务流，如自然推荐、广告和商家服务，用户行为形成连续的跨流轨迹。维护独立的排序系统会割裂用户表示并增加工程成本。我们提出\textbf{OneModel}，一个用于多流最终排名的统一框架。OneModel将异构行为映射到共享事件序列，通过面向动作的骨干网络学习长上下文用户表示，并引入\emph{场景感知信息调制}以平衡跨流迁移与流特定专业化。在生产部署中，OneModel进一步采用分层用户表示、多目标训练以及通过特征分解、用户特征预取、共享用户塔计算和图级推理优化实现的服务端优化。我们在\emph{小红书}生产环境中部署了OneModel，它在强基线上持续获得离线提升，并随上下文长度和模型容量扩展表现良好。在线A/B测试中，探索流的时间花费提升\textbf{+0.33\%}，参与度提升\textbf{+1.25\%}；信息流广告的广告价值提升\textbf{+3.43\%}，点击率提升\textbf{+8.18\%}；商家推荐的DGMV提升\textbf{+1.1867\%}，GPM提升\textbf{+2.1585\%}，验证了统一多流排名作为有效的生产基础。

## Abstract
Platform-scale recommender systems often span multiple business streams such as organic recommendation, advertising, and merchant services, where user behaviors form a continuous cross-stream trajectory. Maintaining separate ranking systems fragments user representations and increases engineering cost. We propose \textbf{OneModel}, a unified framework for multi-stream final ranking. OneModel maps heterogeneous behaviors into shared event sequences, learns long-context user representations with an action-oriented backbone, and introduces \emph{Scenario-aware Information Modulation} to balance cross-stream transfer and stream-specific specialization. For production deployment, OneModel further adopts stratified user representation, multi-objective training, and optimized online serving with feature decomposition, user feature prefetching, shared user-tower computation, and graph-level inference optimization. We deploy OneModel in production at \emph{Xiaohongshu}, where it delivers consistent offline gains over strong baselines and scales favorably with context length and model capacity. Online A/B tests improve Time Spent by \textbf{+0.33\%} and Engagement by \textbf{+1.25\%} in Explore Feed, lift advertising value by \textbf{+3.43\%} and CTR by \textbf{+8.18\%} in Feed Advertising, and raise DGMV by \textbf{+1.1867\%} and GPM by \textbf{+2.1585\%} in Merchant Recommendation, validating unified multi-stream ranking as an effective production foundation.

### 一、论文的核心问题与研究动机

在实际互联网平台，用户的行为往往并不局限于单一业务场景。以小红书为例，用户的完整使用旅程会自然跨越**自然内容推荐（Organic Recommendation）**、**广告（Advertising）**和**商家服务（Merchant Services）**三个不同的业务流。这些流之间存在互补的信号：内容消费往往能反映用户的购买意愿，广告反馈揭示了用户对商业内容的偏好，商家交互又为兴趣建模提供了高价值的监督信号。

然而，传统工业界惯常的做法是为每个业务流各训练一套独立的排序系统。这造成了两大核心问题：

1. **用户表示割裂**：同一个用户在不同业务流的行为历史被拆散到多个独立的模型中，跨流的连续行为轨迹被打破，用户的长程兴趣难以被统一、完整地刻画；
2. **工程成本高企**：重复维护多套“重能力”模块——长序列建模、大规模embedding、内容理解等——带来高昂的计算、存储与工程消耗。而在生成式排序与长上下文的时代，这些能力的成本还在持续增加。

因此，论文提出的核心问题是：**能否将自然推荐、广告、商家服务统一到一个平台级的共享排序基础模型上**，在复用跨流信息提升整体效果的同时，支持各业务流自身的专业化目标，并满足严格的工业生产与在线服务约束。

**意义概述**：OneModel的提出代表了工业推荐系统中一种从“多套垂直分离模型”向“单一平台级统一基础模型”演进的关键范式尝试，旨在将跨流用户行为作为一条连续轨迹来统一建模，是生成式推荐规模化在实际平台落地的重要方向。

### 二、论文提出的方法论

**Overall Architecture**

OneModel整体架构是一个**层次化的跨场景序列建模系统**，由四个关键部分构成：

**1. 统一跨场景表示学习 (Unified Cross-scenario Representation Learning)**

将异构业务流的输入映射到一个统一的“事件序列”空间中：

- **场景感知特征投影**：不同业务流的原始特征（如ID embedding、类别token、稠密特征）用各自的线性投影层 W(s)、b(s) 映射到共享向量空间：
  ```
  e_i = φ(W(s) x_i(s) + b(s))
  ```
- **结构化上下文注入**：再将场景指示(s)、动作类型(a)、时间间隔(Δ_t)、位置编码等上下文信息注入，形成结构化的行为事件token：
  ```
  z_j = e_{i_j} + Embed(s_j, a_j, Δt_j, pos_j)
  ```
  时间间隔采用多频正弦嵌入编码。

**2. 动作导向的长上下文序列骨干 (Action-Oriented Long-Context Backbone)**

以GenRank风格的动作导向骨干为基础，核心是将**动作作为预测目标、商品作为上下文**来建模，而非如HSTU那样将商品与动作token显式交错，从而显著缩短有效序列长度：

- 历史token表示：`e_i = φ(x_i) + φ_action(a_i) + c_i`（统一商品表示 + 动作嵌入 + 结构上下文）；
- 候选商品采用带掩码的动作嵌入 m 以避免目标动作标签泄漏；
- 所有token（历史 + 候选）输入一个共享的因果Transformer解码器，同时施加**因果掩码**（保序）和**候选掩码**（同一请求内候选间禁止互相注意力）：
  ```
  X(l) = H(l-1) + Attn(Norm(H(l-1)); M_causal, M_cand)
  H(l) = X(l) + FFN(Norm(X(l)))
  ```
- 策略上有两个要点值得注意：
  - 在进入序列编码前先做**显式的item与context交互**（侧特征交叉），使序列骨干保持紧凑；
  - 位置与时间编码采用“交互位置 + 请求索引 + 桶化时间间隔 + ALiBi线性偏置”组合，提供相对时间归纳偏置且不增加二次方偏置表开销。

**3. 场景感知信息调制 (Scenario-aware Information Modulation, SAIM)**

为减少混合流token间的干扰，不采用完全独立的分离塔结构，而是在共享FFN中插入一个由场景ID驱动的轻量门控：

```
g_t = σ(W_g e_{s_t} + b_g),  g_t ∈ (0,1)^{d_f}
FFN^{(s_t)}(h_t) = (SiLU(W1 h_t) ⊙ g_t) W2 + b2
```

由此每个token按自身场景对信息流进行“通道级调制”，在**一个共享计算图谱**内实现流依赖的专业化。这样设计的直接优势是：既能避免完全分开各业务流的塔导致过重的结构与管理成本，又不会退化为对各流不分区别的单一变换——实验显示不同流的门控激活值存在有意义的差异（Rec=0.61、Ads=0.54、Merchant=0.58）。

**4. 多目标优化与在线服务策略**

- **端到端联合训练目标**包含三项：①自监督下一项预测（从混合历史中学习通用序列偏好）；②K个流特定预测任务监督（辅助对齐业务目标）；③参数L2正则：
  ```
  L = α·E[-Σ log P(i_{j+1}|S≤j)] + β·Σ λ_k·E[ℓ_k(ŷ(k), y(k))] + γ‖Θ‖²
  ```
  训练时动态设置权重 α 衰减、β 增长；λ_k 与该流验证AUC成反比（对更难的流施以更高权重）；
- 为保证多目标优化稳定，采用**跨流批次采样**避免高频流主导共享骨干，并在预热阶段实行**早期梯度隔离**（暂时切断流塔到骨干的反向梯度）；
- 另有选择性反向传播：只对高困惑度位置计算梯度，跳过简单位置以省训练开销；
- 在线推理采用**解耦架构**：用户状态（z_u = f_θ(H_u)）由长上下文模型增量更新并缓存在低延迟KV存储中，请求时只需向量化批量打分 s = G_Φ(z_u, V)，配合特征分解、用户特征预取、共享用户塔计算和图级推理优化降低时延。

### 六、主要结论与发现

### 七、方法的优点与亮点

**系统级设计上的优势**：

1. 解决了“共享与专门化的张力”这一多场景建模中的核心难点：采用统一骨干 + 轻量化场景门控（SAIM）的中庸路线，既避免负迁移又不落入完全分离的塔结构成本陷阱；

3. 离线评估从训练级、输入级到模块级做逐步拆解，与在线业务指标形成了验证链条，以多线证据逐步确立其模型“融合+提升”的双重主张；
4. 在业务上具有较好的**多业务共生效用**：自然内容—广告—商家三个流的数据互相滋养，低资源业务流最受益，高资源主场景无损伤——这样的增量对平台运营方向有实际意义。

### 八、不足与局限

1. **平台与数据单一**：只在一个平台（小红书）验证，其跨业务差异性（推荐/广告/商家）及流量比（1:0.2:0.15）并不代表所有平台的业务生态，跨平台推广需谨慎；
2. **透明度受限**：工业系统黑盒局限明显——不公开绝对数据规模、算力投入、详尽的训练超参数细节，使得复现与外部验证困难，同时也无法准确评估“统一模型”在效率上的实际总成本对比（虽然单看在线延迟改善显著，但训练成本是多流分别训练的数倍，文中未对此总量的TCO做比较分析）；
3. **基线覆盖面有限**：相比多任务/跨场景建模文献（如PLE、CausalInt等经典方法），论文中未见呈现对这些方法在相同数据上的系统性对比，削弱了对“相比跨场景多任务方法独特优势”的说服力；
4. **长期影响的测量不足**：在线实验虽然做单点长期效果的初步报告，但对商业化偏好变化、用户长期满意度与疲劳度等维度的长期在线观测缺失；离线侧的Click/Like等结果与业务价值之间也只是间接关联；
5. **目标冲突的分析角度有限**：比如广告流曝光下降-1.07%与CTR上升之间的矛盾如何转化为平台上“用户体验”——广告价值之间更全面的权衡，以及增益在不同投放策略间的分布，并未充分讨论；
6. **SAIM的行为解释有限**：论文报告了SAIM门控激活的数值差异（0.61 vs 0.54 vs 0.58），但没有给出更细粒度的通道级分析来说明调制到底在哪些语义维度进行，机制的作用解释仍是暗箱。
